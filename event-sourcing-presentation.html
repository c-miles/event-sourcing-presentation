Pattern #1: Event Notification

Simple pub/sub: "Something happened, you might care"

Source system sends notification, doesn't expect response

Benefits

  • Low coupling between systems
  • Simple to implement

Pitfalls

  • Logic flow becomes implicit and hard to trace
  • Difficult debugging when processes span multiple events

e.g. Stripe webhooks ("payment_succeeded"), Order placed → email + inventory + analytics

[4:30-5:30] First of 4 patterns. Simplest form: "hey, this happened". Low coupling is good, but hidden workflows are bad.

Event Notification Example

Order placed → multiple systems react independently


# Publisher sends notification
class OrderCreatedReactor
  def call(event)
    # Multiple independent actions
    OrderMailer.confirmation(event.order_id).deliver_later
    InventoryService.reserve(event.items)
    AnalyticsService.track("order_created", event.data)
  end
end

# Each subscriber handles the event independently
# No coordination, no return values expected

Perfect for loosely-coupled side effects

[5:30-6:00] Real Rails example. Each system reacts independently. No orchestration, just notifications.

Pattern #2: Event-Carried State Transfer

"Thicc events" containing complete state data

Consumers maintain local copies, no back-queries needed

Benefits

  • Services remain operational when source is down
  • Fast local reads, no network latency
  • Source system not hammered with queries

Trade-offs

  • Duplicate data across services
  • Each consumer manages synchronization

e.g. Customer address change → event contains full customer profile → Billing, Shipping, Marketing all maintain local copies

[6:00-7:00] "Thicc events" gets a laugh and is memorable. Trade coupling for autonomy: services are independent but must manage their own state. Code example next slide shows this in action.

Event-Carried State Transfer Example

Customer Service broadcasts full state to multiple services


# Event contains complete customer state
Events::CustomerUpdated.new(
  customer_id: 123,
  name: "John Smith",
  email: "john@example.com",
  phone: "555-1234",
  address: {
    street: "123 Main St",
    city: "Columbus",
    state: "OH",
    zip: "43215"
  },
  preferences: { newsletter: true }
)

# Each service maintains own copy in own database
class BillingCustomerCache
  def update_from_event(event)
    self.update!(event.data) # Local copy, no queries back
  end
end

# Marketing, Analytics, etc. - all have local copies

No queries back to the source — everything needed is in the event

[7:00-7:30] Events with complete state enable microservices autonomy. Each service (Billing, Marketing, Analytics) has its own database with its own customer copy. If Customer Service goes down, all three still function normally.

Pattern #3: CQRS

(Command Query Responsibility Segregation)

Separate data structures for reads vs writes

Write Model

  • Enforces business rules
  • Validates commands
  • Updates state

Read Model

  • Denormalized for speed
  • Pre-computed values
  • Optimized for queries

Benefits

  • Optimize reads/writes independently
  • Scale read-heavy workloads

Trade-offs

  • Eventual consistency between models
  • Increased system complexity

e.g. Product catalog: millions browsing products, handful updating inventory

[7:30-8:30] CQRS not inherently about events (Fowler warns this is confused). Key: optimize read-heavy systems. Product catalog perfect example: massive read traffic (browsing), minimal writes (inventory/price updates). Fowler warns "often misused" - only use when benefits outweigh complexity.

CQRS Example

Product catalog: browsed constantly, updated rarely


# Write Model - Normalized 'products' table
class Product < ApplicationRecord
  validates :name, :price, presence: true
  validate :price_must_be_positive

  after_update -> { ProductCatalogSyncJob.perform_later(id) }
end

# Read Model - Denormalized 'product_catalog' table
class ProductCatalogReadModel < ApplicationRecord
  # Flattened columns: name, price, stock_level, avg_rating, review_count

  scope :in_stock, -> { where("stock_level > 0") }
  scope :by_category, ->(cat) { where(category: cat) }
  scope :top_rated, -> { where("avg_rating >= 4.0") }
end

# ProductCatalogReadModel.in_stock.by_category("electronics").top_rated
# => [{ name: "Laptop", price: 999.99, stock_level: 15, avg_rating: 4.5 }, ...]

Denormalized read model means no joins, no calculations — just fast queries

[8:30-9:00] CQRS = different tables for writes vs reads. Write to normalized products (enforces rules), async update to denormalized product_catalog (pre-computed ratings/stock). Reads are fast - no joins, no calculations.

Pattern #4: Event Sourcing

Store all changes as immutable events

Current state computed by replaying event history

Benefits

  • Complete audit trail of every change
  • Time travel: query state at any point in history
  • Rebuild state by replaying events

Trade-offs

  • External system integration complexity
  • Storage overhead for event logs

e.g. Shopping cart: ItemAdded, ItemRemoved, CheckoutCompleted → can prove customer removed headphones at 2:15 PM

The Formal Definition

You understand the concept. Here's the technical definition:

"Capture all changes to application state as a sequence of events. These event objects are stored in the same sequence they were applied, for the same lifetime as the application state itself."
— Martin Fowler

Translation:

Every change = one immutable event

Events = append-only log

State = computed from events

[4:45-5:30] Bridge from bank analogy to technical definition. Fowler gives authority, translation makes it digestible. Natural progression: accessible → technical → practical.

Six Building Blocks

1. Command

User's intent to change the system

AddItemToCart

2. Command Handler

Orchestration layer

3. Aggregate

Domain logic, validates rules

ShoppingCart

4. Event

ItemAddedToCart

5. Event Handler

Reacts to events

Append-only, immutable log of all events

[5:30-6:30] Six core building blocks. KEY DISTINCTION: Command Handler = orchestration (loads/saves), Aggregate = business logic (validates domain rules). Handler is application layer glue, Aggregate is domain layer brain. This separation is crucial but often missed.

The Event Sourcing Flow

Command Intent
→
Handler Load
→
Aggregate Validate
→
Event Store
→
Reaction Update

How it works:

1. User clicks "Add to Cart" → creates AddItemToCart command

2. Handler receives command, loads ShoppingCart by replaying past events

3. Cart validates: Is quantity valid? Is item in stock? (business rules)

4. If valid → ItemAddedToCart event produced and saved to Event Store

5. Multiple handlers react independently: update read model, send analytics, reserve inventory

[7:15-7:45] The mechanics of the flow. KEY: Handler reconstructs aggregate state by replaying events (not loading from DB!). Aggregate validates business rules. Events are facts - multiple handlers can react independently and asynchronously. This shows HOW the pieces interact, not just WHAT they are.

The Event Store & Streams

Now that you understand the flow, let's see where this all lives

Event Store (Event Log)

Append-only database that stores all events in one table


EventStore.publish(event)  # Write
EventStore.read_stream("cart-123")  # Read by stream_id

Event Stream

Logical grouping: all events with the same stream_id


Stream: "cart-123"
  ├─ Events::ItemAdded      (t=14:10)
  ├─ Events::ItemRemoved    (t=14:15)
  └─ Events::CheckoutCompleted (t=14:23)

One stream per aggregate. Query by stream_id to get all events for one entity.

[8:15-8:45] FOUNDATION: Event Store is a single events table. Stream is LOGICAL grouping queried by stream_id column (e.g., "cart-123"). This clarifies read_stream() is just a WHERE clause filtering by stream_id. Makes temporal queries make sense in later examples.

Temporal Queries: How They Work

Query state at any point in time


class CartRepository
  def as_of(cart_id, timestamp)
    # 1. Read events for this cart
    events = EventStore
      .read_stream("cart-#{cart_id}")
      .select { |event| event.created_at <= timestamp }

    # 2. Replay events to rebuild state
    replay_events(events)
  end

  private

  def replay_events(events)
    cart = Cart.new
    events.each { |event| cart.apply(event) }
    cart
  end
end

# Usage
cart = CartRepository.as_of(123, Time.parse("2025-11-19 14:30"))
cart.items # => State at 2:30 PM

Filter events by time, replay → time travel

[11:45-12:15] Show HOW temporal queries work. Filter events before timestamp, replay them. This is how we resolve disputes.

Event Replay: Rebuilding State

State is derived from events, not stored


class Cart
  attr_reader :items, :total

  def initialize
    @items = []
    @total = 0
  end

  def apply(event)
    case event
    when Events::ItemAdded
      add_item(event.data)
    when Events::ItemRemoved
      remove_item(event.data)
    when Events::CheckoutCompleted
      complete_checkout(event.data)
    end
    self
  end

  private

  def add_item(data)
    @items << { product_id: data[:product_id], quantity: data[:quantity] }
    @total += data[:price] * data[:quantity]
  end
end

# Replay to get current state
events = EventStore.read_stream("cart-123")
cart = events.reduce(Cart.new) { |c, event| c.apply(event) }
[12:15-12:45] Show the apply pattern. Each event type knows how to update state. Fold/reduce over events to rebuild.

The External Systems Challenge

Fowler's biggest warning: You can't "undo" external actions

The Problem

  • Can't "unsend" an email
  • Can't "uncharge" a credit card
  • Can't undo API calls to 3rd parties

The Solution

  • Gateway pattern with idempotency keys
  • Track what external actions were taken
  • Check before performing action again

This is why ES requires careful integration design

[12:45-13:15] Fowler emphasizes this heavily. ES replay assumes pure functions. External systems break that assumption. Must handle carefully.

Gateway Pattern: Idempotent Actions

Track what was sent, don't resend on replay


class EmailGateway
  def send_order_confirmation(event)
    # Check if already sent
    return if already_sent?(event.id)

    begin
      EmailService.send(
        to: event.data[:email],
        subject: "Order Confirmation",
        body: email_body(event.data)
      )

      track_as_sent(event.id)
    rescue => e
      log_error(event.id, e)
      raise
    end
  end

  private

  def already_sent?(event_id)
    SentEmails.exists?(event_id: event_id)
  end

  def track_as_sent(event_id)
    SentEmails.create!(
      event_id: event_id,
      sent_at: Time.current,
      idempotency_key: event_id
    )
  end
end

# On replay, emails won't be resent because already_sent? returns true
[13:15-13:45] Gateway checks tracking table. If already sent, skip. Event ID as idempotency key. Essential for production ES systems.

Simple PostgreSQL Event Store


-- Events table (append-only)
CREATE TABLE events (
  id UUID PRIMARY KEY,
  event_type VARCHAR NOT NULL,
  data JSONB NOT NULL,
  metadata JSONB,
  created_at TIMESTAMP NOT NULL
);

-- Streams (logical grouping)
CREATE TABLE streams (
  id SERIAL PRIMARY KEY,
  stream_name VARCHAR NOT NULL UNIQUE,
  event_id UUID REFERENCES events(id),
  position INTEGER NOT NULL
);

That's it! Two tables. Simple, scalable, PostgreSQL-native.
